# logger

Библиотека кодового логирования для STM32, из двух независимых частей: встраиваемая
(клиентская, `logger.h`/`logger.c`) пишет логи на STM32 - одна функция логирования события по
коду, источнику и значению, с приоритетами, метками времени (SysTick и опционально RTC),
выводом в отладочный интерфейс (SWO) и опциональной буферизацией и сохранением в
энергонезависимую память; хостовая (серверная, `log_decoder.h`/`log_decoder.c`) разбирает дамп
этой памяти обратно в записи на ПК/сервере, для дальнейшей визуализации. Общее между ними -
только файл `logger_codes.h` (таблица кодов конкретного проекта).

## Возможности

- Один вызов `LOGGER_Log(code, source_id, value)` на событие - код лога (16 бит, задаётся
  пользователем в отдельной таблице под конкретный проект), идентификатор источника (16 бит,
  различает несколько равноправных экземпляров одного и того же кода) и одно сопровождающее
  значение (32 бита).
- 3 уровня приоритета логов (низкий/средний/высокий), назначаются в таблице кодов.
- Каждая запись автоматически получает метку времени: SysTick (`HAL_GetTick()`, мс с момента
  старта) всегда, плюс время RTC (32 бита, формат на усмотрение пользователя), если в
  `LOGGER_Init()` передана функция чтения RTC (используется, только если RTC реально настроен
  и включён в проекте через CubeMX).
- Вывод каждой записи в отладочный интерфейс SWO по умолчанию, без какой-либо инициализации -
  логировать можно сразу после старта прошивки.
- Опциональная своя функция вывода в консоль (заменяет SWO) и своя функция сохранения
  накопленных логов в энергонезависимую память - обе принимают пользовательский `void*`
  контекст.
- Накопление логов в общем статическом буфере (без malloc, до 256 записей по 16 байт) с
  раздельными порогами сброса на каждый уровень приоритета - буфер сбрасывается в память,
  как только по текущему максимальному приоритету накопленных записей достигнут настроенный
  порог.
- Ручной принудительный сброс буфера (`LOGGER_Flush()`).
- Временные метки (`LOGGER_Mark()`) - лёгкий способ зафиксировать факт прохождения контрольной
  точки в коде без привязки к таблице кодов, с подсчётом частоты вызова по запросу
  (`LOGGER_GetMarkFrequency()`), без нагрузки на сам вызов метки.
- Собственные диагностические события библиотеки (инициализация, сброс буфера в память) -
  зарезервированный диапазон кодов `0x0000-0x00FF`.
- `LOGGER_Log()` спроектирована как предельно быстрая горячая функция - вся валидация
  (корректность таблицы кодов и конфигурации) выполняется один раз в `LOGGER_Init()`.
- Хостовый декодер (`log_decoder.h`/`log_decoder.c`, для ПК/сервера) разбирает дамп памяти
  обратно в массив записей с уже подставленными приоритетом и описанием - см. раздел
  "Хостовая часть" ниже.

## Требования к настройке в CubeMX

| Настройка | Значение |
|---|---|
| Debug (SYS → Debug) | `Serial Wire` - нужен для физического канала SWO |
| SWV (Trace) в отладчике/IDE | включить, если планируется смотреть вывод логгера по умолчанию в SWO Viewer |
| RTC (опционально) | включить и настроить, если нужно поле `rtc_time` в записях - и передать свою `rtc_time_fn` в `LOGGER_Init()` |

Если вместо вывода по умолчанию используется собственная `console_fn` (например, вывод в
UART) - настройка SWO не требуется, библиотека сама по себе не занимает никакой периферии.

## Быстрый старт

```c
#include "logger.h"

/* Минимальный вариант - без инициализации, всё идёт в SWO: */
LOGGER_Log(0x0101U, 0U, 42);

/* Контрольная точка в коде, без привязки к таблице кодов: */
LOGGER_Mark(3U);

/* С буферизацией, сохранением в энергонезависимую память и RTC: */
static void my_write_fn(void *context, const uint8_t *data, uint32_t length_bytes)
{
    /* context - то, что передано в write_context; data/length_bytes - пачка
     * записей LOGGER_Record_t подряд, которую нужно записать во флеш/EEPROM. */
    my_flash_write((my_flash_header_t *)context, data, length_bytes);
}

static void my_console_fn(void *context, uint16_t code, uint16_t source_id,
                           LOGGER_Priority_t priority, int32_t value,
                           uint32_t systick, uint32_t rtc_time, const char *description)
{
    my_uart_printf(context, "0x%04X src=0x%04X [%d] %s = %ld (t=%lums rtc=%lu)\r\n",
                   code, source_id, (int)priority, description ? description : "?",
                   (long)value, (unsigned long)systick, (unsigned long)rtc_time);
}

static uint32_t my_rtc_time_fn(void *context)
{
    /* Вызывается, только если реально нужно (RTC настроен через CubeMX). */
    return my_rtc_read_unix_time((my_rtc_header_t *)context);
}

LOGGER_Config_t cfg =
{
    .write_fn        = my_write_fn,
    .write_context     = &my_flash_header,
    .console_fn        = my_console_fn,
    .console_context    = &my_uart_header,
    .rtc_time_fn       = my_rtc_time_fn,  /* NULL, если RTC не используется */
    .rtc_context        = &my_rtc_header,
    .threshold_low     = 32U,  /* низкий приоритет - пишем в память редко */
    .threshold_medium  = 8U,
    .threshold_high    = 1U,   /* высокий приоритет - пишем в память сразу */
};

if (LOGGER_Init(&cfg) != HAL_OK)
{
    /* некорректная таблица кодов (logger_codes.h) или конфигурация */
}

LOGGER_Log(0x0202U, /* source_id = */ 2U, -1);  /* дальше форматирование/буферизация - по конфигурации */
LOGGER_Flush();                                  /* принудительно сбросить накопленное перед сном */

/* Частота вызова метки #3 (вызовов в секунду), считается только по запросу: */
float hz = 0.0f;
if (LOGGER_GetMarkFrequency(3U, &hz) == HAL_OK)
{
    /* использовать hz */
}
```

Коды логов заполняются заранее под конкретный проект в файле [logger_codes.h](logger_codes.h) -
константный массив (код, приоритет, короткое текстовое описание), с рекомендацией по
нумерации диапазонов кодов в шапке файла. Диапазон `0x0000-0x00FF` зарезервирован под
служебные логи самой библиотеки и не может использоваться в пользовательской таблице.

## Интеграция зависимых библиотек

Если логировать через эту библиотеку хочет другая, зависимая библиотека проекта - её коды не
прописываются внутри неё самой, а резервируются централизованно, здесь же, в
[logger_codes.h](logger_codes.h): под неё выделяется отдельный диапазон кодов, отдельный блок
записей таблицы и отдельная триада `#define` - `LOG_ADDR_<ИМЯ>` (адресное пространство, старший
байт кода) → `LOG_OFFSET_<ИМЯ>_<СОБЫТИЕ>` (младший байт) → `LOG_CODE_<ИМЯ>_<СОБЫТИЕ>` (итоговый
код, собранный из двух предыдущих) - всё под одним и тем же `#ifdef LOGGER_ENABLE_<ИМЯ>`. Этот
же приём (`LOG_ADDR`/`LOG_OFFSET`/`LOG_CODE`) используется и для собственных групп проекта в
примере таблицы (`SYSTEM`/`MEMORY`/`SPI`), а не только для зависимостей - единообразия ради и
чтобы перенос любой группы в другое адресное пространство был правкой одного `LOG_ADDR_...`.
Зависимая библиотека использует только выданные ей `LOG_CODE_...`, никогда не пишет код лога как
число. Включение/отключение логов конкретной зависимости - одним `#define LOGGER_ENABLE_<ИМЯ>`
до `#include "logger_codes.h"`; если он не определён, ни записи, ни define'ы этой зависимости не
попадают в сборку - это защищает общую таблицу от бесконечного роста. Полное описание правил и
рабочий пример (`LOAD_PWM`) - в шапке [logger_codes.h](logger_codes.h).

## Хостовая часть - разбор логов (log_decoder)

Отдельные файлы `log_decoder.h`/`log_decoder.c` - для сборки на ПК/сервере, не для STM32.
Не подключают встраиваемую часть (`logger.h`/`logger.c`) и не собираются вместе с ней - общий
между ними только `logger_codes.h`. Разбирают ровно тот дамп байт, что встраиваемая часть
передавала в `write_fn` (массив `LOGGER_Record_t` подряд), в массив декодированных записей с
уже подставленными приоритетом и текстовым описанием - готовый для прохода кодом визуализации
(за пределами этой библиотеки).

```c
#include "log_decoder.h"

/* data/data_length - дамп, прочитанный из энергонезависимой памяти. */
LOGDEC_DecodedRecord_t records[1024];
size_t count = 0;

if (LOGDEC_Decode(data, data_length, records, 1024, &count))
{
    for (size_t i = 0; i < count; i++)
    {
        /* records[i].code/source_id/value/systick/rtc_time/priority/description */
    }
}
else
{
    /* дамп повреждён (длина не кратна размеру записи) либо records мал для всех записей */
}

/* Точечный поиск описания по коду, например для легенды в UI: */
const char *description = LOGDEC_GetDescription(0x0101U);
```

## Честные ограничения

- Вывод по умолчанию (SWO/ITM) работает только там, где физически есть блок ITM:

  | Работает (есть ITM) | Не работает (нет ITM) |
  |---|---|
  | STM32F1 / F2 / L1 (Cortex-M3) | STM32F0 (Cortex-M0) |
  | STM32F3 / F4 / G4 / L4 / L4+ (Cortex-M4) | STM32G0 / L0 / C0 (Cortex-M0+) |
  | STM32F7 / H7 (Cortex-M7) | STM32WB / WL - ядро CPU2, радио-сопроцессор (Cortex-M0+) |
  | STM32L5 / U5 / H5 / WBA (Cortex-M33) | |
  | STM32WB / WL - ядро CPU1, основное (Cortex-M4) | |

  На МК/ядре без ITM обязательно передавайте свою `console_fn` при инициализации, иначе сборка
  не пройдёт.
- SysTick-метки (`HAL_GetTick()`) - миллисекундное разрешение. Для `LOGGER_Mark()`, вызываемой
  чаще ~1 кГц, частота из `LOGGER_GetMarkFrequency()` будет неточной.
- Формат `rtc_time` (Unix-время, BCD и т.п.) полностью на усмотрение пользователя - библиотека
  лишь переносит результат `rtc_time_fn()` в запись как есть, не интерпретируя его.
- Статистика для `LOGGER_GetMarkFrequency()` ведётся только для `mark_id < LOGGER_MARK_MAX_IDS`
  (по умолчанию 32, переопределяется через `#define`) - для больших идентификаторов сам лог
  всё равно происходит, просто без статистики.
- Приоритет у `LOGGER_Mark()` фиксированный (низкий) - настроить его под конкретный проект
  нельзя, в отличие от кодов из пользовательской таблицы.
- Библиотека не потокобезопасна сама по себе (без критических секций внутри) - при вызовах из
  нескольких контекстов прерываний одновременно оборачивайте `LOGGER_Log()`/`LOGGER_Mark()`/
  `LOGGER_Flush()` в критическую секцию самостоятельно.
- Значение, сопровождающее лог - одно 32-битное число (`int32_t`); произвольные буферы/строки
  не поддерживаются.
- Хостовый декодер не выполняет преобразование порядка байт (endianness) - предполагается, что
  хост и STM32 используют одинаковый порядок байт (little-endian - верно для всех STM32 и для
  x86/x64, подавляющего большинства ARM-серверов).
- Хостовый декодер не читает файлы/потоки самостоятельно - принимает уже загруженный в память
  массив байт, чтение из файла/канала связи - задача кода, который его вызывает.
